Section 1: Executive Summary
1. Overall Implementation Condition

The existing repository represents a functional baseline implemented against an outdated specification (documented in docs/handoff.md as "Phases 1–6 Completed"). While the existing codebase contains solid scaffolding for Appwrite Cloud integration, strict TypeScript typing, and Next.js 15 App Router pages, it was architected under assumptions that directly contradict the latest approved business requirements:

Two-Department Model: The existing codebase is hardcoded around exactly two academic departments: Civil (06) and Computer (07). The database, Cloud Functions, and UI lack support for the six approved institutional departments (Computer, Civil, Electrical, Mechanical, Water, Sanitation).
Conflated Department Architecture: The system uses a single attribute (department_code) rather than maintaining two strictly separated attributes: student_department_id (academic jurisdiction) and maintenance_department_id (maintenance jurisdiction). A student cannot select a maintenance department when filing a complaint; complaints are automatically stamped with the student's academic department.
Pervasive Public Complaint Architecture: Public complaint functionality—which has been completely removed in the latest requirements—is deeply embedded across the database schema (issue_type), Cloud Function query logic, frontend form toggles, filter bars, and test suites.
Critical PII Data Leakage: Current API endpoints (handleListComplaints and handleGetComplaint) serialize and return the student creator's full name (student_name) and enrollment number (student_enrollment_no) directly to peer students, violating the mandatory privacy requirement.
Missing Enterprise Workflows: Entire subsystems—including the Principal Role, Five-Day Delay & Warning Logic, Phone Number Change Workflow, Separate Timeline Entries for Complaint Immutability, Support Revocation / Re-Support, and Append-Only Audit History—are 100% missing from the codebase.
Hardcoded Admin Provisioning: Department admin authentication relies on static environment variables (ADMIN_ALLOWLIST_06, ADMIN_ALLOWLIST_07) rather than database-driven, server-enforced, and auditable permission grants.

3. Major Architectural Conflicts
Single Department Field vs. Academic/Maintenance Separation: Current database schema and backend code combine student academic department and complaint target department into a single department_code field. The new requirements mandate strict separation into student_department_id and maintenance_department_id.
Direct Mutation vs. Separate Timeline Immutability: Current admin status updates directly overwrite status, official_response, resolved_at, and updated_at on the complaints collection document. The new specification mandates that original complaint documents remain permanently immutable, with administrator notes and student replies recorded as separate timeline records.
Public Grievance Infrastructure: The concept of issue_type: 'public' permeates database indexes, API queries, feed aggregation, and frontend UI, whereas public complaints have been completely excised.
Static Email Allowlist vs. Auditable Dynamic Roles: Administrator access is hardcoded in functions/campusvoice-api/src/auth.ts via environment variables, completely bypassing database-driven role grants, permission management, and audit tracking.
4. Critical Security Concerns
Critical (P0) — Student PII Exposure to Peers: When any student lists or views complaints in their department, the backend returns the creator's full name and enrollment number in the JSON response payload (functions/campusvoice-api/src/handlers/complaints.ts#L246-L248). The requirement mandates that creator name, enrollment number, phone number, and private attachments must be hidden from peer students.
High (P1) — Unvalidated Attachment IDs & Oversized Storage Limits: In handleCreateComplaint, the API accepts arbitrary attachment_file_id strings without verifying actual file existence, MIME type, or file size. Furthermore, scripts/setup-appwrite.mjs#L303-L304 provisions the storage bucket with a 10MB limit and allows webp, conflicting with the approved 5MB limit and [PDF, JPG, JPEG, PNG] formats.
High (P1) — Non-Atomic Support Counter Concurrency: Support count incrementing in complaints.ts#L647-L656 uses a non-atomic read-then-update pattern on the complaint document rather than deriving support_count = 1 + active_supports, creating counter drift under concurrent traffic.
5. Reusability Verdict

The existing codebase CAN and SHOULD be reused as the foundational baseline. The technology stack (Next.js 15 App Router, TypeScript strict mode, Appwrite Cloud Client & Functions, Tailwind CSS, @phosphor-icons/react) exactly matches the mandatory technology stack. The authentication handshake (Google OAuth via Appwrite Client SDK), the zero-based slice enrollment extraction mechanism (slice(7, 9)), the deterministic SHA-256 voting ID deduplication logic, and core UI layouts provide substantial reusability. A total rewrite is neither necessary nor recommended.

Files: functions/campusvoice-api/src/handlers/complaints.ts#L588-L597

Section 6: Conflicting Implementation

The following existing implementations directly contradict the latest approved business requirements and must be eliminated or refactored:

1. Two-Department Hardcoding
Current Behavior: Codebase assumes only two departments exist: Civil (06) and Computer (07). Seed data (setup-appwrite.mjs#L214-L217), health endpoints (functions/.../index.ts#L52-L55, src/app/api/health/route.ts#L9-L12), and UI banners hardcode this limitation.
New Requirement: System must support six departments: Computer, Civil, Electrical, Mechanical, Water, Sanitation.
2. Conflated Academic and Maintenance Department Logic
Current Behavior: A complaint only has one department attribute (department_code), which is automatically stamped with the student's academic department (complaints.ts#L151). A student cannot file a complaint against a different maintenance department.
New Requirement: Must maintain two separate attributes: student_department_id (academic) and maintenance_department_id (maintenance). Computer, Civil, Electrical, and Mechanical serve academic and maintenance; Water and Sanitation are maintenance-only.
3. Public Complaint System Remains Active
Current Behavior: issue_type: 'public' is defined in types, collections, schemas, creation forms, dashboard filters, and test suites (tests/phase3.test.mjs#L38-L56). Public complaints bypass department isolation.
New Requirement: Public complaint functionality has been completely removed. Every complaint is private to the filer's academic department for peer visibility and routed to the selected maintenance department for resolution.
4. Direct Complaint Document Mutation
Current Behavior: handleUpdateAdminComplaint directly updates status, official_response, and resolved_at on the original complaint document.
New Requirement: Original complaint document is permanently immutable after creation. Admin updates, substantive progress notes, and student replies must be stored as separate records in a timeline collection.
5. Initial Support Count is Zero
Current Behavior: Complaints are created with support_count: 0 (complaints.ts#L159, setup-appwrite.mjs#L266).
New Requirement: Initial support count = 1. Active count = 1 + active support records.
6. Permanent Support Lock (No Revocation)
Current Behavior: Once supported, any subsequent attempt returns HTTP 409 ALREADY_SUPPORTED (complaints.ts#L635-L642), and the frontend button is permanently disabled (ComplaintSupportButton.tsx#L31).
New Requirement: Students must be able to remove their support, and support the complaint again later.
7. Static Environment Allowlist for Admin Roles
Current Behavior: Admin roles are resolved by matching user email against ADMIN_ALLOWLIST_07 and ADMIN_ALLOWLIST_06 in server environment variables (auth.ts#L71-L87).
New Requirement: Department Admins must be assignable and revocable via explicit database-backed permission grants managed by the Principal, with every change audited.

Section 8: Security Audit

Findings are classified by standard severity tiers:

1. Critical Severity (P0)
SEC-01: Direct Exposure of Student Creator PII to Peer Students
Severity: Critical
Vulnerable Code: functions/campusvoice-api/src/handlers/complaints.ts#L244-L263, L434-L453
Description: handleListComplaints and handleGetComplaint map raw database records into the API response without projecting or sanitizing identity attributes. When Student B views complaints from their academic department, the JSON response includes student_name and student_enrollment_no of the complaint author.
Requirement Violated: Requirement F ("When another student views a complaint, hide: Creator name, Enrollment number, Phone number, Private attachments... No student's phone number may be exposed to other students").
Exploitation Scenario: Any authenticated student can call list-complaints or get-complaint via DevTools or API to enumerate full names, enrollment numbers, and grievance history of every student in their academic department.
High-Level Fix: Implement server-side projection in complaints.ts: If caller.id !== complaint.student_user_id and caller is not Admin/Principal, omit student_name, student_enrollment_no, phone_number, and attachment_file_id.
2. High Severity (P1)
SEC-02: Missing Server-Side File Validation & Oversized Storage Limits
Severity: High
Vulnerable Code: functions/campusvoice-api/src/handlers/complaints.ts#L85-L88, scripts/setup-appwrite.mjs#L303-L304
Description: The create complaint endpoint accepts an unvalidated string attachment_file_id without inspecting whether the referenced file exists in Appwrite Storage, whether the caller owns it, or whether its MIME type and byte size conform to policy. The provisioning script sets the bucket ceiling to 10MB (requirement is 5MB) and allows .webp.
Requirement Violated: Requirement E ("Maximum size: 5 MB. Allowed formats: PDF, JPG, JPEG, PNG. Actual file type and size must be validated server-side. Attachments must have private access protection").
Exploitation Scenario: A malicious user could attach arbitrary files up to 10MB or reference files uploaded by other users (IDOR on storage bucket).
High-Level Fix: Enforce server-side inspection via Appwrite Storage API (storage.getFile) verifying size <= 5,242,880 bytes and MIME type in ['application/pdf', 'image/jpeg', 'image/png'].
SEC-03: Hardcoded Admin Assignment & Lack of Revocation
Severity: High
Vulnerable Code: functions/campusvoice-api/src/auth.ts#L71-L88
Description: Admin roles are resolved exclusively by environment variables ADMIN_ALLOWLIST_06 and ADMIN_ALLOWLIST_07. There is no mechanism for dynamic role assignment, role revocation, or Principal oversight.
Requirement Violated: Requirement C & J ("Selected authorized accounts may receive additional system-management permissions through explicit permission grants... Principal can assign and remove Department Admins").
High-Level Fix: Move admin authorization to a dedicated department_admins collection managed by Principal endpoints, with audit logs on assignment/removal.
3. Medium Severity (P2)
SEC-04: Non-Atomic Support Counter Concurrency
Severity: Medium
Vulnerable Code: functions/campusvoice-api/src/handlers/complaints.ts#L647-L656
Description: While unique voter records are deduplicated via deterministic SHA-256 keys, the complaint's support_count is read, incremented in Node.js memory (newCount = currentCount + 1), and written back via databases.updateDocument. Concurrent requests will race, leading to counter drift.
Requirement Violated: Requirement G ("Support count = 1 + active support records. Concurrent support requests must be handled safely").
High-Level Fix: Calculate support_count = 1 + count(active_supports) dynamically or derive it from the active supports collection.
SEC-05: Water & Sanitation Admins Missing Approval Restriction
Severity: Medium
Vulnerable Code: Entire codebase (missing phone change module)
Description: The system lacks any guard preventing Water and Sanitation Admins from performing academic actions such as reviewing student phone changes.
Requirement Violated: Requirement I ("Water and Sanitation Admins cannot approve student phone-change requests").
High-Level Fix: Implement strict department role guards ensuring only academic department admins (Computer, Civil, Electrical, Mechanical) can approve phone change requests for their students.
4. Low Severity (P3)
SEC-06: Cross-Department Oracle Prevention Mismatch
Severity: Low
Vulnerable Code: functions/campusvoice-api/src/handlers/complaints.ts#L457-L471
Description: Oracle elimination returns generic HTTP 404 for cross-department probes, but compares caller department against department_code rather than student_department_id.
High-Level Fix: Realign oracle elimination checks to compare caller's academic department against student_department_id.
5. Informational (P4)
SEC-07: Public Complaint Residual Vectors
Severity: Informational
Vulnerable Code: functions/campusvoice-api/src/handlers/complaints.ts#L281-L329, src/app/complaints/new/page.tsx#L332-L359
Description: Unused public grievance routes and form toggles add attack surface and clutter.
High-Level Fix: Purge all public complaint logic and schemas completely.
